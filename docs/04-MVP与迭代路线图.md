# 云衣柜 · MVP 与迭代路线图

**版本**：v1.0

---

## 一、分期总览

```
Phase 0          Phase 1           Phase 2            Phase 3
数字衣橱 MVP  →  智能 + 生命周期  →  O2O 仓储物流   →  平台生态
(8 周)           (8 周)            (12 周)            (持续)
```

| 阶段 | 代号 | 目标 | 核心交付 |
|------|------|------|----------|
| Phase 0 | **衣橱觉醒** | 验证「用户愿意录入衣物」 | 注册、录入、分类、天气推荐、打卡 |
| Phase 1 | **穿衣自由** | 验证「用户每日使用推荐」 | AI 推荐、保养提醒、捐赠、会员框架 |
| Phase 2 | **云端衣橱** | 验证「用户愿意为物理服务付费」 | 标签体系、仓储入库、异地取还、门店 |
| Phase 3 | **衣橱生态** | 规模化与平台化 | 全国仓储、品牌合作、开放 API |

## 二、Phase 0 — 数字衣橱 MVP（8 周）

### 目标

> 证明用户愿意拍照录入衣物，并使用每日穿搭推荐。

### 功能清单

| # | 功能 | 优先级 | 工作量 |
|---|------|--------|--------|
| 1 | 账号注册 / 登录 | P0 | 3 天 |
| 2 | 新用户云空间赠送弹窗 | P0 | 1 天 |
| 3 | 用户类型选择（学生/上班族/家庭） | P0 | 1 天 |
| 4 | 新手 3 步引导 | P0 | 2 天 |
| 5 | 拍照 / 相册录入衣物 | P0 | 5 天 |
| 6 | 衣物列表 + 分类筛选 | P0 | 4 天 |
| 7 | 衣物详情 + 编辑 + 删除 | P0 | 3 天 |
| 8 | 天气 API 接入 | P0 | 2 天 |
| 9 | 规则引擎今日推荐 | P0 | 5 天 |
| 10 | 「穿上这套」穿搭打卡 | P0 | 3 天 |
| 11 | 首页仪表盘 | P0 | 4 天 |
| 12 | 穿搭记录日历 | P0 | 4 天 |
| 13 | 基础穿搭统计 | P1 | 3 天 |
| 14 | 云空间用量展示 | P0 | 1 天 |

**MVP 不做**：微信登录、社交、电商、O2O、AI 图像识别、会员付费

### 技术交付物

- [ ] `cloudWardrobe`：Expo App 可安装运行
- [ ] `CloudWardrobe`：NestJS 后端 + PostgreSQL
- [ ] Docker Compose 本地开发环境
- [ ] 核心 API 文档（Swagger）

### 验证指标

| 指标 | 目标值 | 未达标则 |
|------|--------|----------|
| 注册 → 录入首件转化率 | ≥ 60% | 优化引导流程 / 简化录入 |
| 7 日留存 | ≥ 30% | 检查推荐质量 / 增加提醒 |
| 人均录入衣物数（首周） | ≥ 5 件 | 增加快速录入 / 批量模式 |
| 每日推荐点击率 | ≥ 40% | 调整推荐算法 / UI |
| 穿搭打卡率 | ≥ 20% | 增加晚间提醒推送 |

## 三、Phase 1 — 智能穿搭 + 生命周期（8 周）

### 目标

> 从「能用的衣橱」升级为「每天想打开的穿搭助手」。

### 功能清单

| # | 功能 | 说明 |
|---|------|------|
| 1 | LLM 智能搭配 | GPT 生成穿搭方案 + 搭配理由 |
| 2 | 图像 AI 预填 | 拍照后自动识别类别和颜色 |
| 3 | 清洗 / 保养提醒 | 基于穿着次数和材质 |
| 4 | 换季提醒 | 基于天气趋势 + 衣物季节标签 |
| 5 | 捐赠申请流程 | 选择衣物 → 生成清单 → 确认 |
| 6 | 折旧估值展示 | 基于年限和状态的参考估值 |
| 7 | 时尚资讯 Feed | 每日 3 条精选穿搭灵感 |
| 8 | 微信登录 | OAuth 接入 |
| 9 | 会员基础框架 | 免费版 / 标准版权益对比 |
| 10 | 数据云同步 | 多设备实时同步 |
| 11 | 离线模式 | 本地缓存 + 联网同步 |
| 12 | 意见反馈 | 应用内文字 + 截图反馈 |

### 验证指标

| 指标 | 目标值 |
|------|--------|
| 30 日留存 | ≥ 20% |
| 日均打开次数 | ≥ 1.5 次 |
| 推荐满意度（5 分制） | ≥ 3.5 |
| 捐赠 / 保养功能使用率 | ≥ 10% |

## 四、Phase 2 — O2O 仓储物流（12 周）

### 目标

> 验证「异地取还」核心商业模式，单城单店试点。

### 功能清单

| # | 功能 | 说明 |
|---|------|------|
| 1 | 唯一标签体系 | RFID / 二维码生成与绑定 |
| 2 | 仓储入库流程 | 用户发起 → 快递揽收 → 仓库扫码入库 |
| 3 | 异地取衣预约 | 选择城市 + 衣物 + 取件方式 |
| 4 | 门店自取 | 预约到店时间 + 二维码核销 |
| 5 | 快递配送 | 填写地址 + 物流跟踪 |
| 6 | 门店换衣服务 | 旧衣洗护 + 新衣出库 |
| 7 | 定期保养服务 | 预约 + 进度跟踪 |
| 8 | 门店管理后台 | 扫码入库/出库、订单管理 |
| 9 | 支付集成 | 微信支付（服务费） |
| 10 | 物流 API | 顺丰 / 菜鸟对接 |

### 试点方案

```
城市：上海（1 个中央仓 + 2 个门店）
用户：50 名内测用户
周期：4 周封闭测试
```

### 验证指标

| 指标 | 目标值 |
|------|--------|
| 入库完成率 | ≥ 90% |
| 取衣满意度 | ≥ 4.0 / 5.0 |
| 付费转化率 | ≥ 15% |
| 单用户月均服务费 | ≥ ¥30 |

## 六、功能优先级矩阵

按 **用户价值 × 实现成本** 排序：

```
高价值 │ ★ 拍照录入      ★ 今日推荐       ○ 异地取还
       │ ★ 分类搜索      ★ 穿搭打卡       ○ 门店换衣
       │ ★ 注册登录      ○ AI 智能搭配    ○ 跨国仓储
       │ ○ 保养提醒      ○ 捐赠流程       ○ 开放 API
───────┼────────────────────────────────────────────
低价值 │ ○ 时尚资讯      △ 微信登录       ✕ 即时通讯
       │ ○ 折旧估值      △ 会员积分       ✕ AR 试穿
       │ ○ 数据报表      △ 价格对比       ✕ 完整电商
       │
       低成本 ──────────────────────────── 高成本

★ = Phase 0 (MVP)    ○ = Phase 1-2    △ = Phase 1-3    ✕ = 不做或远期
```

## 八、风险与应对

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| 用户不愿录入衣物 | 高 | 致命 | 极简录入 + 门店代录入 + 快速模式 |
| 推荐质量差 | 中 | 高 | MVP 用规则引擎保底，逐步引入 LLM |
| O2O 物流成本高 | 中 | 高 | 单城试点，验证单位经济模型 |
| 衣物损坏纠纷 | 中 | 中 | 入库拍照存证 + 保险合作 |
| 竞品模仿 | 低 | 中 | 快速建立仓储网络壁垒 |
| 隐私数据泄露 | 低 | 致命 | 加密 + 审计 + 渗透测试 |

## 九、下一步行动项

### 立即可做

1. **确认 MVP 范围**：本文 Phase 0 功能清单
2. **搭建 Monorepo**：前端 + 后端项目骨架
3. **设计数据库 Schema**：基于技术架构文档的数据模型
4. **UI 原型**：首页 + 录入 + 衣橱 3 个核心页面
5. **注册后端域名 + 云服务**：准备开发环境

### 需要决策

| 决策项 | 选项 | 建议 |
|--------|------|------|
| 仓库结构 | Monorepo vs 多仓库 | Monorepo（小团队） |
| MVP 推荐方案 | 纯规则 vs 规则+LLM | 纯规则（降本） |
| 首批试点城市 | 上海 / 北京 / 深圳 | 选团队所在城市 |
| 仓储模式 | 自建 vs 第三方合作 | 第三方合作（降初期投入） |
